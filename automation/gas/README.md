# 経理メール自動化（Google Apps Script）

`docs/accounting-email-rules.md` で定義したルールを実行するスクリプト。
Gmail・Google Drive・スプレッドシートを横断して、分類・保存・返信下書き・督促の起票を自動化する。

---

## 設計方針

| | |
|---|---|
| **送信は必ず人が行う** | 先方宛のメールは**下書きまで**しか作らない。金額と信用に直結する文書であり、誤送信のコストが自動化の便益を上回る（ルール §12.1） |
| **人の入力を機械が壊さない** | 台帳の更新は「空欄を埋める」のみ。ステータスは前進のみ許可し、`入金済`・`相殺・精算済` は終端として巻き戻さない |
| **判定できない時は督促しない側に倒す** | スレッド参照に失敗した場合などは、督促をスキップする |
| **freee には触らない** | 税区分修正が完了するまで freee 連携は作らない。`30_経理/入出金（自動投入）` は `po_agent` の領域のため出力先にしない（ルール §11） |

## なぜ Gmail フィルタではなく Apps Script なのか

Gmail のフィルタは取引先マスタを参照できず、条件が固定文字列に限られる。
送信元から取引先を引く、発注書番号を抽出する、Drive にフォルダを作る、
営業日で督促日を計算する ── いずれもフィルタでは表現できない。
分類もまとめて Apps Script 側に寄せている。

## セットアップ

### 1. プロジェクトを作る

[script.google.com](https://script.google.com) で新規プロジェクトを作成し、
このディレクトリの `.gs` と `appsscript.json` を貼り付ける。

> `appsscript.json` を編集するには、エディタの「プロジェクトの設定」で
> 「`appsscript.json` マニフェスト ファイルをエディタで表示する」を有効にする。

### 2. Script Properties を登録する

**このリポジトリは公開のため、ID・口座情報・担当者氏名はソースに含めていない。**
エディタの「プロジェクトの設定 > スクリプト プロパティ」から手で登録するか、
`Setup.gs` の `initProperties()` のプレースホルダを埋めてローカルで1回だけ実行する。

| キー | 内容 | 必須 |
|---|---|:--:|
| `LEDGER_ID` | 経理_請求管理台帳（自動連携）のスプレッドシートID | ✓ |
| `MASTER_ID` | 経理_取引先マスタのスプレッドシートID | ✓ |
| `CLIENTS_FOLDER_ID` | `10_クライアント（受発注・請求・納品）` のフォルダID | ✓ |
| `ARCHIVE_FOLDER_ID` | `90_アーカイブ（旧データ・過去分）` のフォルダID | ✓ |
| `NOTIFY_TO` | 社内リマインドの送信先 | ✓ |
| `BANK_BLOCK` | 振込先口座の文面ブロック（改行込み） | ✓ |
| `SIGNATURE` | メール署名ブロック（改行込み） | ✓ |
| `CONTACT_{コード}` | 取引先の担当者名。例 `CONTACT_WLB` | 任意 |
| `ESCALATION_CC_{コード}` | 二次督促以降で追加するCc。`;` 区切り | 任意 |

### 3. 動作確認 → トリガー登録

```
healthCheck()      // 設定・マスタ・台帳・ラベルの疎通を確認（破壊的操作なし）
dryRunDunning()    // 督促の判定結果だけを出力（下書きもメールも作らない）
dryRunReplies()    // 返信要否の判定だけを出力（下書きを作らない）
installTriggers()  // 問題なければトリガーを登録
```

2つのドライランの出力を必ず目視してから `installTriggers()` を実行すること。

## トリガー

| 関数 | 間隔 | 動作 |
|---|---|---|
| `runInboxSweep` | 1時間ごと | `classifyInbox()` → `fileSentInvoices()` → `draftReplies()` |
| `runDailyDunning` | 平日 09:00 JST | 督促判定・下書き作成・社内ダイジェスト送信 |

`runInboxSweep` は `LockService` で多重実行を防いでいる。

## 処理の流れ

```
発注書メール受領
   ↓ classifyInbox()
   ├─ 取引先ラベル + 02_発注書/未対応 + 99_要対応
   └─ fileIncomingPurchaseOrder()      ← S1
        ├─ 10_クライアント/{会社}/{年}/YYMMDD【発注書No】案件名  を作成
        ├─ 発注書の原本を保存
        └─ 台帳に「未送付」で起票（請求書番号を §3 の書式で採番）

請求書を送信（人が送る）
   ↓ fileSentInvoices()
   ├─ 添付を案件フォルダへ保存         ← S2
   ├─ 台帳を「入金待ち」へ・支払期限を算出
   └─ 02_発注書/請求済 + 01_請求/送付済 + 01_請求/入金待ち

日次 09:00
   ↓ runDailyDunning()
   ├─ 期限 -3営業日 → 社内リマインドのみ（先方には送らない）
   ├─ 期限 +1営業日 → 入金照合の対象として社内へ通知
   ├─ 期限 +3 / +10 / +20営業日 → 督促の下書きを作成（未送信）
   └─ 督促前に3点確認（ルール §8.3）を必ず通す
```

## 督促前の3点確認

過去に精算済み案件を督促した事例があるため、`dunningPreCheck()` で必ず検査する。

1. ステータスが `相殺・精算済` でないこと
2. 先方から入金予定日の回答が来ていないこと（回答済ならその日まで督促しない）
3. 該当スレッドに先方からの支払関連の返信が来ていないこと

いずれかに該当した場合は督促せず、理由を社内ダイジェストに載せる。

## 運用上の注意

- **下書きは自動送信されない。** Gmail の下書きを開き、§7 のチェックリストを通してから送信する
- **三次督促は代表の承認が必要。** ダイジェストにその旨を明記している。電話併用のこと
- 台帳の `入金日` `入金額` は人が記入する。記入後、次回実行でステータスが `入金済` として扱われる
- マスタ未登録の取引先からのメールは分類のみ行い、フォルダ作成と台帳起票はしない（採番衝突の防止）
- 既存の案件フォルダは `【発注書No】` で照合するため、旧命名 `…発注書・前金` のままでも新規作成にはならない

## 返信下書きの自動生成（`Reply.gs`）

受信メールを3つに振り分ける。**どの区分でも送信はしない。**

| 区分 | 種別 | 動作 |
|---|---|---|
| **返信不要** | `NO_REPLY` 送信専用・マーケティング<br>`RECEIPT_ACK` 「拝受しました」だけの受領連絡 | 何もしない |
| **定型** | `PAYMENT_NOTICE` 入金連絡 → お礼（台帳から金額を引く）<br>`DUE_DATE_CHANGE` 支払期日の変更申し出 → 承諾 | 完成形の下書きを作る |
| **要判断** | `PO_RECEIVED` 発注書受領<br>`INVOICE_RESEND` 再送依頼<br>`INVOICE_ERROR` 誤りの指摘<br>`DELIVERY_INQUIRY` 納期照会 | 骨子を作り、埋める箇所を `《　》` で明示する |
| **人が見る** | `JUDGMENT` 上記に当てはまらないもの | 下書きを作らず `99_要対応` を付ける |

判定できないものは `JUDGMENT` に倒す。**機械が勝手に文面を作らない**のが原則。

`《　》` が本文に残っている下書きはそのまま送れない。これは意図した設計で、
機械が持っていない事実（金額・納期・送信記録）を人が埋めるための空欄である。

多重生成は次の3点で防いでいる。

1. 対象メッセージより後に自社から返信していれば何もしない
2. そのスレッドに既に下書きがあれば触らない
3. 前回実行時刻以降の新着のみを走査する

## 実装していないこと

- **freee 連携** ── 税区分修正の完了後（ルール §11.3 の順序に従う）
- **請求書PDFの自動生成** ── Phase 2 の範囲。現状は人が作成した添付を保存するのみ
- **入金明細の自動照合** ── Phase 3。現状は照合対象を社内通知するところまで
