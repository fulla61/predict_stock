## 1. UX Principles（最上位UX原則）

### 1.1 三者それぞれへの「見え方」の定義（ARCHITECTURE_LOCKに準ずる設計判定基準）

| 利用者 | システムの見え方 | 絶対に見せないもの |
|---|---|---|
| 顧客（CLIENT） | 「業務管理システム」ではなく、**Crossimageと会話・確認しながら自然に商品化まで進むサービス**。画面は「会話の続き」であり「管理画面」ではない | Project DNA / Commercial Profile / Rule Engine / Cost Ledger（費用台帳）/ Commercial Feasibility Loop（条件すり合わせの往復）の管理構造 / State Machine / Reference Set / テーブル構造・内部ID・enum・89テーブルの存在そのもの |
| Crossimage社内 | **判断だけが並ぶ机**。情報の一覧ではなく「今日決めること」が上から降りてくる | 判断材料の収集・比較・転記・計算の作業画面（それらはSystem/AIが済ませてから人間に渡す） |
| 中国側（CN_OFFICE / FACTORY） | CN_OFFICEには**今日やることが中国語で最小限に並ぶ道具**。工場には**道具を変えさせない**（Excel / WeChat / PDF / 写真・動画が第一級チャネル。Portalは閲覧補助） | 顧客販売価格・粗利・他工場情報（Governance §8）。および日本側の業務構造 |

### 1.2 Actionの正準セット（これ以外の操作を三者にさせない）

| 利用者 | 許可されるAction | 禁止される作業（=System/AIの仕事） |
|---|---|---|
| 顧客 | **INPUT（入力）/ DECIDE（選ぶ）/ APPROVE（承認する）/ CHECK（確認する）** | 進捗管理・ステータス更新・資料整理・二重入力・翻訳・比較表づくり |
| Crossimage人間 | **DECIDE / APPROVE / NEGOTIATE（交渉）/ EXCEPTION（例外対応）/ CRITICAL ISSUE対応** | 転記・翻訳・比較・計算・要約・資料作成・進捗更新・催促・差分抽出（Governance §16「Human Decision Pointの最適化」・22番§10.1） |
| CN_OFFICE | 取込確認・差分レビュー・現物判断（検品・首件等）・工場との折衝 | 帳票の手作り・日本側への転記報告・翻訳作業（AIドラフトの確認のみ） |
| FACTORY | Excel記入・WeChat回答・写真/動画送付・签回（サイン返送） | Portalログイン・システム操作の強制 |

### 1.3 「作りたいを育てる」心理順序（顧客向け全Flow共通の情報提示順）

顧客向けの提案・見積・Loop・リスク説明は、必ず次の順で情報を出す。**逆順（リスクや制約から先に見せる）を禁止**する。ただし安全・法規のEarly Warning（11番§4.3）のみ早期表示の例外とする。

```
DESIRE（作りたい気持ち）→ POSSIBILITY（できそうだ）→ PROPOSAL（こういう形はどうか）
→ FEASIBILITY（工場確認でここまで見えた）→ TRADE-OFF（何を取り何を譲るか）
→ RISK + COUNTERMEASURE（重点管理ポイントと当社の対策）→ DECISION（あなたが選ぶ）
```

- 内部の顧客心理Status（IDEA〜ORDERED。11番§1.1）はこの順序のトラッキング指標であり、顧客に露出しない。
- 「できません」単独提示の禁止（Governance §16）はこの順序の系である: 不成立は必ずTRADE-OFF段階の情報（何を維持し何を変えるか）として提示する。

### 1.4 画面に関する成果の定義

1. **画面数を増やすことを成果としない。** 成果は 入力回数・画面遷移数・二重入力数・人間の管理作業時間の最小化（§15のUX Metricsで計測）。
2. 新画面の追加は、§5の10検証質問を全て通過した場合のみ許可する（1つでも「統合可能」「Drawer/Modal/Inlineで済む」「AIで消せる」に該当したら独立画面にしない）。
3. 同一情報の二重表示・同一入力の二重要求は欠陥として扱う（SpecField / Commercial Profileの参照一本化。22番P-15と同根）。
4. すべての画面はStateで変化する「キャンバス」であり、工程ごとに別画面を作らない（§5の統合仮説の基本原理）。

## 2. Role Model（利用文脈・デバイス・頻度）

| Role | 利用文脈 | 主デバイス | 想定頻度 | UX上の含意 |
|---|---|---|---|---|
| CLIENT（初心者） | 本業の合間に「自分の商品」を進める。専門知識ゼロ。夜間・移動中の利用が多い | **スマホ優先** | 週1〜3回・1回5〜15分 | 1画面1判断・選択式中心・片手操作・「次に決めることは1つ」提示（19番§3.2） |
| CLIENT（プロ/調達担当） | 業務として複数案件を比較検討。仕様書・CADを持つ | PC優先+スマホで承認 | 週数回・短時間で密度高く | FAST TRACK・一括Upload・専門用語直接表示（Q1〜Q4開示。11番§9） |
| SALES | 顧客提案の承認・価格判断・顧客折衝。外出あり | PC+スマホ（承認・通知確認） | 毎日 | Decision Queue中心。承認はスマホ完結可 |
| PM（商品開発） | 工場選定・仕様・サンプル判断 | PC中心 | 毎日 | One Decision画面+Drill Down。詳細分析はDesktop優先 |
| QA | 品質基準・検品結果・限度見本の判断 | PC中心+現物写真確認はタブレット/スマホ | 案件イベント時 | 写真・動画の比較表示が主要素 |
| REG（法規） | 法規判定・試験手配の最終判断 | PC | 案件イベント時（低頻度・高重要） | 判断待ちキューのみ。BLOCKED理由と解除条件の明示 |
| TRADE（貿易） | 船積・通関・関税確認 | PC | 出荷期に集中 | 期限駆動の例外リスト中心 |
| MGR | Hard Gate承認・高額/低Margin案件の最終判断 | **スマホ完結を許容**（承認）+ PC（分析） | 毎日・短時間 | 承認6点セットの1画面提示。代理承認者への自動引継 |
| CN_OFFICE | 工場との折衝・Excel往復・検品立会。移動が多い | **スマホ（WeChat併用）+ PC（取込・差分レビュー）** | 毎日 | 中国語最小UI。「今日やること」1列。取込はPC、確認・承認・写真はスマホ |
| FACTORY | 生産現場。Portal強制しない | WeChat（スマホ）+ Excel（PC） | 依頼駆動 | **Portal画面を前提にしない**（画面数カウント外。12番§2の設計をそのまま採用） |

- 同一画面のRole別表示差分は§14。FACTORYはPortal任意利用時も「同一データのExcelを常に取得可能」（Governance §11-1）。

## 3. Information Architecture（3者別の情報空間）

### 3.1 3層の情報空間と翻訳境界

```
[内部構造の空間]  Project/DNA/Profile6種/Loop/Quote版/Cost Ledger/Gate/Task/enum —— 89テーブルの世界
        │  ↑ここは「機械と社内の言葉」。境界を越えるとき必ず翻訳する
        ├──(顧客語翻訳層)──→ [顧客の空間]   「あなたの商品」「いまの状況」「次に決めること」「選べる進め方」
        ├──(業務語翻訳層)──→ [社内の空間]   「今日決めること」「承認待ち」「例外」「停止中」
        └──(中文翻訳層)────→ [中国側の空間] 「今日任务」「待回复」「本期限」「变更点」
```

- 翻訳層は19番の用語辞書+表示名マップが実装する（enum生値を表示するコードパスを持たない=19番§2.3-4）。本書は「どの内部概念を、どの空間で、何と見せるか」の対応を規定する。

### 3.2 顧客に見せる情報 / 見せない情報の対応表（裏側複雑性の隠蔽マッピング）

| 内部の実体（見せない） | 顧客に見せる表現（見せ方） | 根拠 |
|---|---|---|
| CommercialLoop（LOOP-NN・State Machine） | 「**条件を調整して、より合う方法を探しています**」+ 選べる進め方A/B/C | Governance §16 / 11番§10 |
| CustomerDecision enum 7分岐 | 「そのまま進める / 条件を変える / 交渉してもらう / 別の工場を探してもらう / もう一度見積をとる / しばらく保留にする / 今回は見送る」ボタン | 11番§10.4 |
| Commercial Profile / BudgetStatus / QuantityStatus | 「ご予算・数量は決まっていなくて大丈夫です」+ 決まった時点で「あなたの決定🔒」へ記録 | Governance §0-6 |
| Project DNA 8軸 | 一切見せない。効果（質問の数・説明の詳しさ・確認の密度）としてのみ体感させる | Governance §4 |
| Rule Engine / Rule Pack / 属性タグ | 「この商品に必要な確認を当社が整理しました」（結果のみ） | Governance §13 |
| Cost Ledger / Landed Cost / Margin | **内部原価・Margin・他工場見積は絶対非表示**。顧客にはQuotation（顧客見積書）の金額と「概算/正式」の区別のみ | Governance §8/§17 |
| Quote（工場見積）生数値・工場名・工場比較 | 「工場からの回答」欄に当社が整理した要約1枚（工場名なし） | 11番§10.1 |
| Gate（G-01〜G-16）・Readiness判定 | 「あと○○がそろえば次に進めます」（不足の顧客語訳）。Hard Gate停止は「当社で確認中です（完了見込み○日）」 | 19番§4.2 |
| Task / Task Generator / WAITING_* | 「当社が進めていること」「次にお決めいただくこと」の2欄に翻訳 | 11番§6.2 |
| SpecField Status 4値 | 「確定 / 検討中」の2値表示。AI_SUGGESTEDは「当社の想定（変更できます）」 | 11番§6.2 / §7（本書） |
| Reference Set / Golden Sample手続 | 「量産の基準を一緒に確定します」（必要物だけを1つずつ依頼） | 22番§11 |
| Regulatory State Machine | 「法律で定められた検査：当社で手配・対応中」+ ⚠Early Warning | 11番§4.3 |
| ProductFeedback分類14種・原因区分 | 「使ってみていかがですか」（会話式。クレームフォームにしない） | §8.6（本書） |
| 心理Status（IDEA〜ORDERED） | 完全非表示 | 11番§1.1 |

### 3.3 社内・中国側の情報空間（要点）

- 社内: 内部実体は「見せてよい」が、**生データではなく判断材料の形**（6点セット: 顧客希望/工場回答/差分/Cost・Margin/Risk/AI推奨。22番§10.2）でのみ提示する。enum・Gate IDは日本語主+括弧コード（19番§4.3）。
- CN_OFFICE: 中国語最小UI。情報空間は「今日任务（今日やること）」「待回复（未回答）」「变更点（変更点）」の3語彙に集約（12番§2.3のDigest構造と同一語彙にし、画面とWeChatの認知を一致させる）。
- FACTORY: 情報空間はExcel 13シート+WeChatDigestが正（12番§2）。本書はFACTORY向け新画面を定義しない。

## 4. Navigation Architecture（Portal別ナビ構造）

### 4.1 CLIENT PORTAL — 「NEXT DECISION」中心（メニューを覚えさせない）

```
ホーム = あなたの商品（商品カード1枚 or 複数カード）
  └ 商品カードを開く → 「あなたの商品」ページ（単一キャンバス。§5 SC-C3）
      ├ 最上部: 次にお決めいただくこと（NEXT DECISION。0〜3件。0件なら「当社が進めています」）
      ├ いまの状況（7段階の平易表現）
      ├ 工場からの回答（届いたときだけ出現 → 「進め方を見る▶」= SC-C4へ）
      ├ これまでの経緯（条件変更履歴・常設）
      └ ご相談・お声（自由文。Feedbackもここから=フォームを分けない）
```

- **グローバルナビを実質廃止**する（「ホーム/あなたの商品」のみ）。顧客の行き先は常にNEXT DECISIONが指す1箇所。
- 新規相談はホームの入力欄（SC-C1）から。リピートは商品カードの「同じものをもう一度」から（§8.5）。
- 深い階層・パンくず・サイトマップ型ナビを作らない（会話サービスの見え方を壊すため）。

### 4.2 TRADING CO PORTAL — 「Decision Queue」中心

```
ホーム = 今日の判断（SC-S1）
  ├ 1. 今日決めること（C_HUMAN_DECISION）      → 1クリックでOne Decision画面（SC-S2）
  ├ 2. 承認待ち（Approval=PENDING）            → 同上（承認もOne Decision型）
  ├ 3. 例外リスト（§9.2の11類型）              → 該当のOne Decision画面 or 案件360
  ├ 4. 停止中（Hard Gate）                     → 解除条件の充足画面リンクのみ（解除ボタンなし）
  ├ 5. 待ち（顧客待ち/中国側待ち。閲覧のみ）    → 催促はA_FULL_AUTO（人間は押さない）
  └ 案件360（SC-S3。検索/一覧からのDrill Down専用。正常案件はここに「行かない」のが正常）
```

- **正常進行中の案件はホームに出さない**（Exception Driven Operations。§9.2）。「見に行く」ナビではなく「降ってくる」キューが正。
- 案件横断の一覧・検索は補助導線（ヘッダ検索1つ）。一覧画面を業務の起点にしない。

### 4.3 FACTORY/CHINA PORTAL（CN_OFFICE用） — 「今日やること」中心・中国語

```
首页 = 今日任务（SC-N1）
  ├ 今日任务（期限順1列: 询价下发/报价回收/打样跟进/检验/装柜…）
  ├ 待回复（工場からの未回答・期限超過の催促キュー。Digest送信はここからワンタップ）
  ├ 收件箱（工場からの返信Excel/WeChat/写真の取込待ち → 取込・差分レビュー画面 SC-N2へ）
  └ 变更点（新版発行・作废通知の送達確認）
```

- タブは最大4つ。案件別ページは持たず、Taskから該当案件のコンテキストを開く（案件を探させない）。
- 出货批准（出荷承認申請）だけはPortal上のApproval操作のみ有効（12番§2.1原則2）をナビ上も特別扱い（今日任务の最上位固定）。

## 6. Adaptive Customer Entry（6入口を単一UXで吸収する設計）

### 6.1 原則: 入口を選ばせない

6つの入口意図 —— ①相談したい ②商品決定済み ③写真・URLだけある ④仕様書・CAD保有 ⑤数量・予算だけ決まっている ⑥リピート —— を**別システム・別フォーム・入口選択画面にしない**。SC-C1の単一キャンバスが全てを受ける（11番§2「入口選択画面は設けない」の拡張正式化。Entry Route A〜Dは内部分類のまま維持し顧客に見せない）。

### 6.2 Conversation First + Dynamic Form のHybrid

```
SC-C1 相談キャンバス
┌────────────────────────────────────────────┐
│ 「どんな商品を作りたいですか？」                  │
│ ［自由文入力欄］［画像］［PDF/仕様書/CAD］［URL］  │ ← 何をどの組合せで入れてもよい
├────────────────────────────────────────────┤
│ (AIが裏で構造化: Known/Missing/Conflicting/      │ ← 顧客には見せない
│  Assumption/Critical Missing + Route/DNA推定)     │
├────────────────────────────────────────────┤
│ 応答は入力の性質に適応:                            │
│  ①相談だけ → 共感+BLOCKERのみInline質問(最大3問)  │
│  ②商品確定 → 確認カード「この内容で見積に進めます」│
│  ③写真/URL → 解析結果カード「こう理解しました」    │
│  ④仕様書/CAD → 抽出一覧の確認へ直行(質問・教育抑止)│
│  ⑤数量/予算のみ → 「商品はこれから一緒に」提案起動 │
│  ⑥リピート → ログイン済なら商品カード提示へ誘導    │
└────────────────────────────────────────────┘
```

設計規定:
1. **会話が主・フォームが従**: 画面の骨格は「入力 → AIの理解の提示 → 不足のBLOCKERだけ質問」の会話ループ。Dynamic Formは会話の中に必要なときだけ現れる構造化入力カード（選択肢・数値・日付・アップロード）であり、固定の長いフォームを最初に見せない。
2. **詳細保有者は一括、0知識は少しずつ**: 添付ファイルの解析結果（SpecField化）を確認カードで見せ、確定済み情報には**二度と質問しない**（§7-1）。0知識顧客には1画面最大3問・選択式優先（11番§3.3を継承）。
3. **途中で性質が変わってよい**: 相談で始めた顧客が途中で仕様書を投げ込んだら、その時点でFAST TRACK相当に適応（Route/DNAの内部更新。顧客に「モードが変わった」と見せない）。
4. **既存顧客のリピート**: SC-C1に入力しなくても、SC-C3の商品カード「同じものをもう一度」が最短経路（§8.5）。SC-C1に「前回のタンブラーをまた…」等と書かれた場合もAIが商品を特定しRepeat Flowへ接続する。
5. 会話ログ・添付・AI構造化結果はすべてRequirement/SpecField/Commercial Profileへ格納され、以降の全画面・全Routeで共有（二重入力禁止の実装点）。

## 7. Minimum Question Engine UX

### 7.1 質問分類とUX規定

| 分類 | UX上の扱い |
|---|---|
| BLOCKER | 即時・Inline質問カード（最大3問/画面）。「あとで答える」を常設（G-10はSoft） |
| IMPORTANT_LATER | その情報が必要になる工程の直前にJust-in-Time表示（11番§3.3） |
| OPTIONAL | 質問せず既定値（AI_SUGGESTED）で進行。設定は「あなたの商品」内で任意変更可 |
| **AI_INFERABLE（新設提案）** | **質問自体を出さない**。AIが推測可能な項目は推測して進み、推測値は「当社の想定（変更できます）」として可視化のみ行う。→ §18 Governance変更提案① |

- AI_INFERABLE新設の趣旨: 現行3分類では「Assumptionの確認」をOPTIONALとして質問リストに残す構造だが、質問ゼロ化のためには「**そもそも質問候補にしない**」クラスが必要。QuestionClass enumの拡張はGovernance §3の変更手続対象のため、本書は勝手に使用せず§18で起案する（採用までは OPTIONAL + 非表示運用で同等効果を出す）。

### 7.2 再質問禁止と推測値の非昇格（UI表現）

1. **既知情報の再質問禁止**: 回答・添付解析・前回案件（Client Knowledge）・会話中の言及から判明済みの項目は、全Route・全工程・全画面で質問候補から除外（target_spec_fieldキーで排除。18番§8.2の機構を表示層でも保証）。
2. **AI推測（AI_INFERRED表示）を顧客確定へ勝手に昇格させない**: 推測値は常に「当社の想定: ステンレス真空断熱（変更できます）」形式の**想定カード**で表示し、内部StatusはAI_SUGGESTEDのまま保持。「あなたの決定🔒」（青枠・日時付き）への昇格は顧客の明示的な確定操作のみで発生する（11番§5の3分離表示を判定基準とする）。
3. 想定カードの一括確定UI（「当社の想定でまとめて進める」）は許可するが、その場合も操作証跡（どの項目を・いつ・一括確定したか）をAuditLogに残し、確定画面で対象一覧を明示する（黙って昇格させない）。
4. Conflictingは質問でなく「確認」（例:「画像は450mlに見えますが、文章では350mlとありました」）。顧客を責める文言禁止（11番§3.2-2）。

## 8. 主要Flow群（画面IDは§5.4のAFTER仮説を使用）

### 8.1 Customer Journey Screen Flow（初回・0知識〜プロ共通の骨格）

```
SC-C1 相談キャンバス（入力→AI理解→BLOCKERのみ質問）
  → SC-C2 プランを固める
      State1: ご提案A/B/C（心理順序: DESIRE→POSSIBILITY→PROPOSAL）
      State2: 段階質問（品質4択・色・数量。Just-in-Time教育カード）
      State3: 実現確認（3分離表示: あなたの決定🔒/当社のおすすめ💡/工場からの回答🏭）→ 確定
  → SC-C3 あなたの商品（以降のホーム。「ここからは当社の出番です」）
  →（工場回答到着）→ SC-C4 進め方の選択 → SC-C3 …（Loop周回。§8.4）
```

- 顧客操作は初回入力→提案閲覧まで**3ステップ以内**、各Loop周回**3画面以内**（11番/22番§18合格基準を画面構造として保証: **不成立周回=SC-C3の回答欄→SC-C4の2画面 / 成立周回=SC-C3内確認カードの1画面**。UX-RT是正#4）。
- プロ（FAST TRACK）はSC-C1で一括Upload→SC-C2のState2を抽出結果確認に差替え→確定（教育・提案を抑止。同一画面のRole/DNA差分であり別Flowにしない）。

### 8.2 Internal Decision Flow（社内）

```
SC-S1 今日の判断（キュー降着: 判断/承認/例外/停止中）
  → SC-S2 One Decision画面（1画面=1判断。6点セット提示）
      → APPROVE / MODIFY / NEGOTIATE / RE_SOURCE / REJECT（+理由）
      → 後続はSystemが自動起票（JP-LOOP-030等）。人間は次のキューへ
  →（深掘りが必要な例外のみ）SC-S3 案件360 → SC-S2へ戻って判断
```

- **原則「判断はSC-S2で完結」**。SC-S3へ降りるのは例外時のみ、比較元Excelを開かせない（22番§10.2受入基準）。承認・判断・交渉指示はすべて同一型のUIで行い、操作学習を1回で済ませる。

### 8.3 China Operation Flow（CN_OFFICE）

```
SC-N1 今日任务（期限順1列）
  ├ 下発系: RFQ/仕様書/品質基準のExcel+Digestをワンタップ送信（生成はSystem済み）
  ├ 回収系: 待回复の催促Digestワンタップ / 受信物は收件箱へ
  → SC-N2 取込・差分レビュー（AI取込済みの差分・矛盾・空欄だけ確認 → SoT昇格操作）
  └ 現場系（検品・首件・装柜）: スマホで写真・チェックリスト・判定入力（SC-N1のTaskカード内で完結）
```

- 工場との実通信はWeChat/Excelのまま（12番§2）。PortalはCN_OFFICEの「変換コストを払う場所」であり、工場を巻き込まない。

### 8.4 ★Commercial Loop Screen Flow（顧客に「Loop管理」を見せない）

顧客への見せ方の原則: 画面上に「ループ」「周回」「LOOP-02」等の管理概念を出さない。**「条件を調整して、より合う方法を探しています」という自然な会話の続き**として提示する。

```
[内部] Quote取込 → JP-LOOP-010分析 → JP-LOOP-020 Option生成→SALES承認
[社内] SC-S2（Loop判断: 6点セット+5ボタン。顧客提示前の関所）
[顧客] SC-C3「🏭工場からの回答が届きました」通知+要約
        ├ 成立 → **SC-C3内**確認カード「この内容で進めますか？」→そのまま進める（ACCEPT）
        │        （SC-C4へ遷移しない=UX-RT是正#4。成立周回の顧客画面はSC-C3の1画面で完結）
        └ 不成立/条件付 → SC-C4「選べる進め方」（SC-C4は不成立・条件付専用）
             ・Option提示数は可変（案件・DNAで決定。EXP_BEGINNER=おすすめ1+代替最大2 /
               それ以外=全Option+比較表。3固定にしない=22番§21のCALIBRATION）
             ・Option型の例: おすすめ / MOQ優先（数量を活かす）/ 価格優先 / 品質優先 /
               ODM優先（オリジナル性を守る）等から案件に応じ選定
             ・各Optionの必須表示7項目: 特徴（何を維持し何を変えるか）/ 概算価格 / MOQ /
               初期費用 / 納期 / 良い点 / 妥協点+注意点 —— すべて「工場確認中の目安」注記付き（G-15拡張）
             ・7分岐ボタン（11番§10.4文言）+「相談したい」常設
[顧客] 決定 → SC-C3「これまでの経緯」に自動記録（いつ・何を・なぜ、を顧客語で）
[内部] JP-LOOP-030 → 新Loop行/Profile新版/後続Task → 次周回へ
```

- 待機中の顧客表示: 「当社が工場と交渉しています（回答目安◯日）」等、**誰が何をしている途中か**を常時明示（§13）。
- 周回数が閾値超過（CALIBRATION）したら社内にのみP-9アラート（顧客には見せない）。

### 8.5 Repeat Order Flow（「前回と同じ」or「ここだけ変更」起点）

```
SC-C3 商品カード「同じものをもう一度」タップ
  → 確認カード（1枚）: 「前回と同じ内容で進めます」
      ├ 変化項目のみ表示: 数量［前回値がプリセット］・希望時期［「前回と同程度」プリセット=UX-RT是正#7。変化ゼロなら入力0］
      ├ System再確認8項目（価格/MOQ/材料/納期/運賃/為替/法規/部品供給。22番§16）の結果、
      │  **変化があった項目だけ**「前回から変わった点」として顧客に提示（例: 為替影響で単価目安+3%）
      └ 「ここだけ変更したい」→ 変更したい箇所を選ぶ → 該当項目だけSC-C2のState2形式で再質問
  → 確定 → 即RFQ_READY判定（仕様再入力ゼロ）
```

- 変化ゼロなら顧客操作は**2タップ+確定**。仕様変更ありは内部でECRフローへ接続（顧客には「変更内容の確認」とだけ見せる）。

### 8.6 Product Feedback Flow（クレームフォームにしない）

```
納品後30/60日: 「使ってみていかがですか？」通知（能動収集Task）
  → SC-C3内のご相談・お声欄（自由文+写真/動画。選択肢は「よかった点/気になる点/改善してほしい点」の3トーン）
  → AIがFeedbackType/重症度を裏で分類（顧客に分類を選ばせない）
  → 重大事案の兆候（安全・怪我・重大不良）のみ即時に社内Exception昇格+顧客へ「担当者よりご連絡します」
  → それ以外は「貴重なお声をありがとうございます。次の改善に活かします」+ 対応した場合は後日
     「あなたのお声を反映しました」（Evolution Flowへ接続）
```

- 「問題報告=クレーム=責任追及」の空気をUIから排除する（原因未確定のうちは中立トーン。Governance §19の証跡設計は内部で実施）。Complaint昇格・CAPA・原因区分は内部処理であり顧客画面に出さない。

### 8.7 Product Evolution Flow（顧客には「何が改善されたか」中心）

```
[内部] Feedback蓄積 → V1.1候補の差分生成（v_product_version_diff）→ SALES承認
[顧客] SC-C3に改善提案カード:
  「前回の商品から、ここが良くなります」
   ・改善点1（対応したお声: 「フタが開けにくい」→ 開けやすい形状に変更）
   ・改善点2 … / 変わらない点（価格・品質基準の維持）/ 費用・納期への影響
  → 「この改善で次回を作る」（Repeat Flowに合流）/「今回は前回のまま」
```

- 顧客に見せる軸は「前回から何が改善されたか」のみ。BOM差分・工場差分・コスト内訳差分等の内部7比較軸は社内（SC-S3）専用。

## 9. One Decision Screen設計 + Exception Driven Operations（社内）

### 9.1 One Decision Screen（SC-S2）構造規定

```
┌─ 1画面=1判断 ──────────────────────────────┐
│ [判断名] 例:「CI-2026-0001 Loop判断: 希望数量と工場条件に差」│
│ ① 顧客希望（Commercial Profile最新版の要点）              │
│ ② 工場回答（Quote版の要点。複数社はSystem統合済み差分のみ）│
│ ③ 差分（価格/MOQ/納期/仕様/初期費用の不一致点だけ）        │
│ ④ Cost・Margin（8分類集約+確度表示。§10.1）               │
│ ⑤ Risk（該当例外・Gate・Confidence）                      │
│ ⑥ AI推奨案+根拠（1案+代替）                               │
│ [APPROVE] [MODIFY] [NEGOTIATE] [RE_SOURCE] [REJECT] +理由 │
│ ▼詳細を見る（Drill Down Drawer: Quote全版/費目明細/履歴）  │
└──────────────────────────────────────────┘
```

1. 判断に必要なデータは**すべてこの画面に集約済み**であること（実装受入基準）。**複数のExcel・PDF・画面を並べて人間に比較させる導線を禁止**する（比較・差分抽出はSystemの仕事。22番§10.2）。
2. 承認（Proposal送信・Quotation・PO・ShipmentRelease等）も同型で提示する（①〜⑥の内容が判断種別ごとのデータ差になるだけ。ボタンはAPPROVE/REJECT/CONDITIONAL系に縮退）。
3. Drill Downは同一画面内のDrawer（遷移させない）。Drawer内も表示のみで転記入力を発生させない。
4. 判断ボタン+理由入力の操作証跡はapprovals/audit_logsへ（既存機構）。

## 10. Cost UX / Quality UX / Risk UX

### 10.1 Cost UX

**社内**:
1. 費用は**8分類（製造/開発・初期/品質・試験/中国国内/国際物流/日本輸入/日本国内物流/その他・例外）へまとめて表示**し、必要時のみ費目明細へ展開する（Drawer。初期表示で89費目を並べない）。
2. 全金額に**確度バッジを必須表示**: 「概算（AI推定含む）/ 見積あり（Quote・第三者見積）/ 確定 / 実績」（内部enum CostStatusの表示訳。ESTIMATED・AI_ESTIMATEDは「概算」に束ね、AI推定はさらに「AI概算」注記）。確度混在の合計値には「概算含む」を強制表示し、見積と実績の混同をUIでも禁止する（Governance §17）。
3. Quotation承認画面（SC-S2）にConfidence低・ESTIMATED費目残数・DutyStatusを強制表示（22番P-10/P-11）。
4. Landed Cost（着地原価）は概算/確定/実績の3段階を並べて乖離を見せる（KPI入力）。

**顧客**: 内部原価・Margin・他工場見積・内部リスクコストは**絶対非表示**（全チャネル。Governance §8 v3.1）。顧客に見せる金額はQuotation由来のみで、「概算（工場確認前/確認中の目安）」か「正式なお見積り」かを常に明示（G-15）。費用が動くときは「黙って上げない」: 変化額+理由+選び直し導線をセットで提示（11番STEP9の原則を全Flowに一般化）。

### 10.2 Quality UX

1. 顧客には4択のみ: 「コスト重視/標準/ブランド重視/プレミアム」（16番§5.3の文言・内部Tier変換をそのまま採用）。AQL/CTQ/検査水準は見せない（EXP_PROFESSIONALのみTier詳細開示可）。
2. 各選択肢に概算コスト差（Q2比±%レンジ）と推奨バッジを併記。**品質変更の影響説明を必須**とする: 選択変更時に「何の確認が増える/減るか」「費用目安±」「どんなリスクが残るか」を顧客語で即時表示（16番§5.2の項目単位提示を顧客語に翻訳）。
3. 「どのレベルでも、安全と法律に関わる項目は同じ厳しさで必ず確認します」を選択肢の下に固定表示（FIXED MINIMUMの顧客語訳）。
4. サンプル確認（顧客）は「見るべき点リスト」（QualityProfile重点項目由来）を写真・動画と並べ、項目ごとに「OK/気になる」の2値+自由文で回収する（検査用語を出さない）。

### 10.3 Risk UX

顧客への提示順序を固定する（§1.3の心理順序のRISK段の詳細化）:

```
① 重点管理ポイント（何を重点確認するか。「リスク」という語を使わない）
② 起こりうること（可能性。頻度・条件を平易に）
③ 当社の対策（試験・検品・限度見本・立会等）
④ それでも残ること（残余リスク。正直に）
⑤ お客様の判断（進める/条件を変える/相談する）
```

- Safety/Legal該当は例外: ⚠Early Warning（黄色帯）で**早期・明確に**表示し、G-03 BLOCKは「進行が止まること」を隠さない（顧客語では「法定検査の完了をお待ちください+当社対応中+見込み日」）。
- 社内はRiskを⑤例外リスト・6点セット⑤欄で提示（同一データの Role別ビュー）。

## 11. Notification Architecture

原則: **Portalを毎日開かなくても案件が止まらない**。通知は「開かせるため」ではなく「判断・入力を届けるため」に送る。

| 優先度 | 定義 | チャネル既定 | 例 |
|---|---|---|---|
| ACTION_REQUIRED | 受信者の入力・決定・承認がないと進まない | メール/LINE/WeChat+Portal内バッジ。期限付きはリマインド有 | Option選択依頼・ロゴ入稿依頼・承認依頼 |
| RISK | 判断は不要だが知らないと損害があり得る | 同上（リマインドなし・1回） | 納期遅延見込み+新目安日・検品NG発生 |
| INFORMATION | 進捗・完了の共有 | 週次ダイジェストに集約（即時送信しない） | 「見積依頼を送りました」・週次経過報告 |

通知過多防止ルール:
1. **重複禁止**: 同一事象は1受信者に1通。Portal内表示と通知の二重催促をしない（通知→開いたらバッジ消込）。
2. **束ね**: 同一案件のINFORMATIONは週1のダイジェストへ集約（空白週も1行は必ず出す=11番§6.2「空白期間を作らない」）。ACTION_REQUIREDは束ねない（単独で届く）。
3. **上限と昇格**: 1受信者あたりの通知日次上限（CALIBRATION）。上限超過時はINFORMATIONから間引き、ACTION_REQUIRED/RISKは間引かない。未反応のACTION_REQUIREDのみ段階リマインド→社内エスカレーション（N-04等の既存ルール）。
4. **文面**: 通知単体で完結（何が起きた/なぜ/次に何をする/期限）。リンク先は該当の1画面（SC-C4・SC-S2等）へ直行し、ホーム経由の迷子を作らない。
5. 中国側はWeChatDigestの既存規律（週1+イベント駆動・日次禁止・15行以内。12番§2.3）を通知アーキテクチャの一部としてそのまま採用。
6. 通知にも情報遮断を適用（メール本文・プッシュ・Digestに原価・Margin・工場名等を含めない。Governance §8 v3.1）。

## 13. Error / Empty / Waiting / Blocked State Design

共通原則: 全State表示は「①何が起きているか ②誰が何をしている途中か ③次に何が起こるか（目安日）④あなたがすること（なければ『お待ちいただくだけで大丈夫です』）」の4点構成。日付なしの待機・遅延表示を禁止（11番§6.2）。

| # | 状況 | 顧客表示（要旨） | 社内/中国側表示 |

| 5 | Quoteなし（見積未着のまま期限接近） | 表示変更なし（顧客に催促状況を見せない） | 例外#4（回答遅延）へ昇格 |

## 14. Permission-based Display Rules（同一画面のRole別表示差分）

1. **画面は共有・欄は遮断**: 同一画面IDに対しRole別の欄マスクを定義する（画面を増やさず表示差分で対応）。遮断は「欄ごと非表示」であり「値だけ伏字」にしない（存在自体を知らせない）。

## 18. Governance変更提案（1件）

> Governance Pack冒頭表の変更手続に従い起案する。**採否確定まで本書は現行3分類の枠内で運用可能な設計とした**（§7.1のとおりOPTIONAL+非表示運用で暫定代替可）。

### 提案①: QuestionClass enumへの `AI_INFERABLE` 追加

- **内容**: Governance §3 QuestionClass を `BLOCKER / IMPORTANT_LATER / OPTIONAL / AI_INFERABLE` の4値へ拡張する。
- **定義**: AIが既存情報（入力・添付・Client Knowledge・Rule Pack既定）から十分な確度で推測可能な項目。**質問として顧客に提示しない**。推測値はSpecField `AI_SUGGESTED` として保持し、顧客画面では「当社の想定（変更できます）」として可視化のみ行う（§7.2の非昇格原則に従う）。
- **理由**: 現行3分類はすべて「質問リストに載る」前提であり、「質問自体を発生させない」分類が構造上存在しない。Questions Before Project Start（§15指標2）の最小化と、既知情報の再質問禁止をエンジン仕様として明確化するために必要。
- **影響範囲**: questions分類ロジック（Requirement Analyzer / Rule Pack QuestionListの分類出力）にのみ追加。既存3分類の意味・G-10の対象（BLOCKERのみ）は不変。confidence閾値（AI_INFERABLE判定の線）はCALIBRATION_VALUE。
