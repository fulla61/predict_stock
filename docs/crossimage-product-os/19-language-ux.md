## 0. 適用範囲と基本原則

1. **適用範囲**: UI上の全専門用語 / 顧客向け説明文 / Workflow説明 / Dashboard表示（顧客・社内とも） / エラーメッセージ / 工場向け指示文（中国語）。
2. **正準キー（EN）は表示層に生のまま出さない**（§14）。DB・API・enum・内部設計記述での正準キー使用は本書の対象外（違反ではない）。
3. **初出時フォーマット（§14必須）**: `用語（日本語説明：短い定義）`。例: `MOQ（最小発注数量：工場が受けられる最低ロット）`。
4. **表示は日本語主・英語従**。英語略語が業界標準として通用する語（MOQ・AQL等）は英語表記を残してよいが、必ず日本語説明を伴わせる。装飾目的の英語見出し（例: CURRENT STATUS）は日本語を主表記とする。
5. **中国語UIも同原則**: 中文用語+説明（§3.4）。製造現場慣用語を使い、日本語直訳を禁止する。

## 1. ★表示用用語辞書（Glossary）

### 1.1 辞書の位置付けとフォーマット

- 本辞書は **表示層のSoT** である（§14「表示用の用語辞書は19番文書で管理する」）。Governance §1 の正準キーが存在する語はそのキーを `term_key` に流用し、存在しない語は本書で表示用キーを定義のうえ §1 への追加を Governance変更提案①として起案する（末尾）。
- 各語は次のフィールドを持つ: `term_key` / `表示名（ja_label）` / `短い定義（short_def）` / `具体例（example）` / `影響（impact：知らないと何を間違えるか）` / `関連用語（related）` / `中文表示（zh_label）`。
- **レベル別表示文は下記の合成規則で機械的に生成する**（辞書に3文を重複保存しない。表示文＝フィールドの合成）:

| ExperienceLevel | 表示文の合成規則 | 例（MOQ） |
|---|---|---|
| `EXP_BEGINNER`（完全説明） | `表示名＋「：short_def」をインライン展開 ＋ 💡具体例 ＋ ⚠影響`（初出時。カード形式で本文中に展開） | MOQ（最小発注数量：工場が一度に受けられる最低の注文数）💡例: MOQ 1,000個→999個以下は受注不可 ⚠これより少ない数量では小ロット対応の工場を探す必要があります |
| `EXP_INTERMEDIATE`（簡易説明） | `表示名（short_def）`（初出時のみ。2回目以降は表示名のみ+Tooltip） | MOQ（工場が一度に受けられる最低の注文数） |
| `EXP_PROFESSIONAL`（用語のみ） | `表示名` のみ。ただしTooltipは常に利用可（§14） | MOQ |

- `EXP_BEGINNER`: 「AQL（合格品質水準：抜き取り検査で合格と判定できる不良率の上限基準）」＋「💡例: 1,000個から108個を抜き取り、重要な不良が基準数以下なら合格。⚠全数検査ではないため、基準の厳しさは品質レベルと一緒に決めます。」

## 2. Tooltipデータ構造とUI仕様

### 2.1 データ構造

用語辞書はDB（glossary_termsテーブル想定・A3整合）＋設計SoTとして本書で管理する。1語のレコード構造:

```yaml
term_key: MOQ                    # 正準キー（§1流用 or 本書起案）。表示層に生で出さない
ja_label: MOQ（最小発注数量）      # 表示名（日本語主表記）
short_def: 工場が一度に受けられる最低の注文数量
example: "MOQ 1,000個 → 999個以下は受注不可（小ロット不可・量産前提）"
impact: 小ロット希望なのに量産前提の工場・見積を選んでしまう
related: [Tooling, LeadTime, Quote]   # term_keyの配列（表示時はja_labelへ解決）
aliases: [ミニマム, 最低ロット, 最小ロット]   # 自動検出用の同義語（表示には使わない＝§1同義語禁止と両立）
level_visibility:                 # ExperienceLevel別の既定表示（§1.1の合成規則）
  EXP_BEGINNER: FULL_INLINE       # 完全説明インライン展開
  EXP_INTERMEDIATE: SHORT_INLINE  # 表示名（短い定義）
  EXP_PROFESSIONAL: TERM_ONLY     # 表示名のみ
zh_label: 最小起订量（MOQ）        # 中国語UI・工場向け文書用
zh_short_def: 工厂可接受的最低下单数量
audience: [CLIENT, INTERNAL, FACTORY]  # 表示可能な相手（情報遮断: GrossMargin等はFACTORY/CLIENT除外）
```

- `audience` は Governance §8 の情報遮断を辞書レベルで担保する（例: `GrossMargin` は FACTORY 向けチャネルに出現したらビルド/生成時エラー）。
- 用語の追加・改訂は A9 起案 → 承認（Approval記録）。承認前の語はTooltipに出さない。

### 2.3 用語の自動検出とマークアップ規則（正準キーを表示層に出さない仕組み）

**原則: 文言ソースは正準キーで参照し、レンダラーが辞書経由で表示文へ解決する。表示文字列に正準キーを直書きしない。**

1. **マークアップ**: テンプレート・AI生成文言は `{{term:MOQ}}`（またはHTMLでは `<span data-term="MOQ">`）で用語を参照する。レンダラーが閲覧者の実効レベル（§3）と初出/再出を判定し、§1.1の合成規則で `ja_label` ベースの表示文へ展開する。**`data-term` の値（正準キー）はDOM属性としてのみ存在し、テキストとして描画されない。**
2. **未登録キーはビルド/生成時エラー**: 辞書に無い `term_key` の参照は、開発時はビルドエラー、AI生成時は承認画面WARN（B_AI_DRAFT の human_action で捕捉）。「とりあえず英語のまま出す」フォールバックを持たない。
3. **自動検出（AI生成文・自由記述の取込文）**: 出力パイプラインの最終段に用語スキャナを置く。(a) `ja_label`・`aliases`・英語略語の最長一致で辞書語を検出し `{{term:…}}` を自動付与、(b) 辞書外の英大文字略語パターン（`[A-Z]{2,}`、正規の製品型番等は許可リストで除外）を検出したら**§14違反候補としてWARN**を出し、人間承認なしに顧客・工場向けチャネルへ送信できない。
4. **enum・Statusの表示禁止の実装**: 表示層に渡るデータのenum値（例: `WAITING_CHINA` / `Q3_PREMIUM` / `REVIEW_REQUIRED`）は、UI側で必ず表示名マップ（本辞書＋Status対訳表）を通す。マップ未定義のenumが画面に到達したら開発環境では例外、本番ではプレースホルダ「（表示名未定義）」＋内部アラート。**enum生値をそのまま文字列表示するコードパスを持たない。**
5. **同義語の統一**: `aliases` はあくまで検出用。表示は常に `ja_label` 一本（§1「表にない同義語の使用は禁止」と整合。例:「検査/検品」の揺れは出荷前現物検査＝「出荷検品」に正規化）。
6. **略語衝突の検出**: 同一略語が複数語に一致する場合（例:「PL」→ ポジティブリスト/PL法/パッキングリスト）は自動付与せず必ず人間確認に回す。表示層では衝突略語の単独使用を禁止し、フル表記（「ポジティブリスト」「PL法（製造物責任法）」「パッキングリスト（梱包明細書）」）を強制する。

### 2.4 中国語UI・工場向け文書への適用方針

1. **同一原則の鏡像**: 中文用語+説明 `术语（说明：一句话定义）`。初出時に説明付き、以降は用語のみ+Tooltip（FACTORY PORTAL）。辞書は同一 `term_key` で `zh_label` / `zh_short_def` を持つ（§2.1）＝日中で語の対応が常に1:1に保たれ、翻訳揺れを防ぐ。
2. **製造現場慣用語を正とする**（A5ルールブックと整合）: 交期（納期）・签样（ゴールデンサンプル）・首件・试产 等。日本語漢字の直用（様品→样品）・日本語直訳調を禁止。
3. **非インタラクティブチャネル（Excel・WeChat要約）**: ホバー/タップが使えないため、(a) 本文初出時は `术语（说明）` を全展開、(b) Excelには**用語対照表シート**（zh_label / 说明 / 日本語対応語）を自動添付、(c) WeChatDigestは要約という性質上、辞書語のみ使用し新規略語を出さない。
4. **工場側レベル別表示は行わない**: 工場は専門家前提のため `TERM_ONLY` 相当を既定とするが、日本固有制度（ポジティブリスト・家品法・PSE等）は**中国側にとっての「専門用語」**であるため、初出時説明を必須とする（例: 日本食品卫生法肯定列表（即日本法规允许用于食品接触的物质清单））。
5. **情報遮断**: `audience` にFACTORYを含まない語（粗利・顧客見積・他工場情報）は中国語チャネルの生成時に混入スキャン対象（10-a1のRFQ生成スキャンと同一機構）。

## 3. レベル別説明ルール（ExperienceLevel連動）

### 3.1 表示切替仕様

- 入力: ProjectDNA の `ExperienceLevel`（`EXP_BEGINNER / EXP_INTERMEDIATE / EXP_PROFESSIONAL`）＋ユーザーの手動上書き（§3.3）。
- **実効レベル = 手動上書き値 ?? DNA値**。DNAが `AI_SUGGESTED` のままでも表示切替は有効（Soft運用）。DNA自体は書き換えない（DNAは案件属性、表示レベルは閲覧設定。混同禁止）。
- 切替対象: 用語の展開度（§1.1）/ Just-in-Time教育カードの表示（11-a2 §4.1と整合: 全表示/折りたたみ/非表示）/ 質問文体 / 「次に決めること」ガイドの粒度。
- 同一案件を複数人が見る場合、実効レベルは**ユーザー単位**で保持（担当者はプロ表示、顧客側の別担当は初心者表示、が両立する）。

| 項目 | EXP_BEGINNER | EXP_INTERMEDIATE | EXP_PROFESSIONAL |
|---|---|---|---|
| 用語表示 | 完全説明インライン展開（初出） | 表示名（短い定義）（初出） | 用語のみ |
| Tooltip | 利用可 | 利用可 | 利用可（常時・§14） |
| 教育カード（💡） | 全表示 | 詳細折りたたみ | 非表示 |
| 新出専門用語数の上限 | 1画面3語（超過分は次画面へ段階提示） | 1画面6語目安 | 制限なし |
| 数値・規格の提示 | 変換して提示（例:「1,000個中108個を抜き取り」） | 規格値+補足（例:「AQL 1.0（抜取基準）」） | 規格値そのまま（AQL 1.0 / Ac=5,Re=6） |
| 次に決めることガイド | 強化（§3.2） | 標準（Dashboard NEXT DECISION） | 最小（一覧のみ） |

### 3.2 初心者モードUI（EXP_BEGINNER）

1. **説明インライン展開**: 初出用語はTooltipを待たず本文中にカード展開（§1.1のFULL_INLINE）。「読み飛ばしても操作が完結する」ことを保証する（説明カードは操作ボタンの間に挟まない）。
2. **専門用語数の制限**: 1画面の新出辞書語は最大3語。設計時にこれを超える画面は分割するか、用語を伴わない言い換え（例: Pantone → 「色見本の写真アップ」）で受け、内部で正準値化する（11-a2 §3.3の既存原則を用語辞書側から保証）。
3. **「次に決めること」ガイド強化**: 全画面下部に固定バーで表示 —「いま決めること（1件）/ あとで決められること（n件）/ 当社にお任せいただけること（n件）」の3分類。各項目に理由一行（「→ 数量で1個あたりの価格が大きく変わるため」）。未回答でも進める導線（Soft Gate範囲）を常に併記する。
4. **不安低減の定型**: 選択肢には必ず「わからない → おすすめで進める」を含める（`AI_SUGGESTED` で進行）。確定操作の直前には「この確定で費用は発生しません」等の影響明示を必須とする。
5. **禁止**: 初心者モードでの英字略語の単独出現 / 1画面4語以上の新出用語 / 「詳しくはヘルプ参照」型の外部誘導（その場理解の原則違反）。

### 3.3 ユーザーによる手動切替

- 画面右上に常設トグル **「説明の詳しさ: ていねい / ふつう / プロ向け」**（内部で `EXP_BEGINNER / EXP_INTERMEDIATE / EXP_PROFESSIONAL` にマップ。enumは新設しない）。
- 切替は即時反映・ユーザー設定として保存。**DNAの `ExperienceLevel` は変更しない**（表示上書きのみ。DNA変更はGovernance §4の履歴手続が必要）。
- 手動で「プロ向け」に切り替えた初心者ユーザーがTooltip多用・エラー多発の場合、AIが「ていねい表示に戻しますか？」を1回だけ提案してよい（強制切替は禁止）。
- 切替状態はテレメトリ記録し、DNA推定（`AI_SUGGESTED`）の補正材料としてよい（自動確定はしない）。

## 6. Governance変更提案

Governance Pack の変更手続（冒頭表・§9）に従い、以下3件を統合レビュー（14番）へ起案する。採否確定まで、本書は既存枠組み（§1既存キー＋本書ローカル定義）で運用可能な記述としている。

### 提案①: §1 Canonical Glossary への21語追加

本書§1.2の辞書語のうち正準キー未定義の21語を §1 へ追加登録することを提案する（DB・API・帳票生成が共通キーで参照するため正準化が必要。表示名・中文は本書§1.2に準拠）:

`CTQ / AQL / OEM / ODM / BOM / CAD / Incoterms / HSCode / EtdEta / BL / PSE / FoodContactPositiveList / AcRe / LandedCost / Pantone / GrossMargin / Gasket / PowderCoating / LaserEngraving / NeedleDetection / DropTest`

- 備考: `GrossMargin` は中文欄なし（情報遮断対象・Quotationと同扱い）を明記することを併せて提案。
- 新Status・新enumの提案はなし（`level_visibility` の値 FULL_INLINE/SHORT_INLINE/TERM_ONLY は辞書データの属性値でありシステムStatusではない。承認StatusはApproval enum流用）。

### 提案②: §14 への補記「表示層の見出し・ラベルは日本語主・英語従」

現行§14は「英語のみでの専門用語提示」を禁止するが、既存成果物には**英語主+日本語従**の見出し（例: CURRENT STATUS いまの状況 / WAITING_CLIENT（顧客待ち））が残る（§5の#3・#7・#11等）。判定基準を明確化するため、§14に次の一文の追記を提案する: 「UI見出し・ラベル・通知文面は日本語を主表記とし、英語・正準キーは括弧内の従表記に限る（装飾目的の英語先行見出しを含め、英語主表記を禁止）。」

### 提案③: §14 への補記「略語衝突時のフル表記義務」

同一略語が複数の意味を持つ場合（本プロジェクト実例: PL = ポジティブリスト / PL法〔製造物責任法〕 / パッキングリスト、AI = 人工知能 / Adobe Illustrator形式）、表示層・顧客向け文書・工場向け文書では当該略語の単独使用を禁止し、フル表記または `略語（正式名）` を義務付けることの明文化を提案する。衝突の検出は19番辞書の `aliases` 照合で機械的に行う（本書§2.3-6）。
