# クロスイメージ株式会社 経理メール運用ルール v1.0

制定日: 2026-08-14 / 対象アカウント: `trade@crossimage.jp` / 所管: 経理

> **本書の位置づけ**
> 本書は「人が読んで守る規程」であると同時に「機械が実行できる仕様書」として書かれている。
> 各ルールは *判断の余地を残さない* 形（採番式・日数・完全一致文字列）で定義する。
> 曖昧さが残る箇所は §10 の例外処理に必ず落とす。ここが崩れると自動化が成立しない。

## 0. なぜルールが必要か（現状の課題）

2026年6月〜8月の実際のメール運用から抽出した、自動化を阻んでいる4つの要因。

| # | 課題 | 実例 |
|---|---|---|
| 1 | 請求書番号の採番規則が取引先ごとにバラバラ | `CRS-4002-1` / `3000-0-2` / `PO-947_1` / `HZ-S-260803` / `EVO-260724` / `CRS-GirlsDesk_20260727_1` が併存。2026-06-26に採番誤り（3001→3000）が発生し訂正メールを送付 |
| 2 | 支払条件が案件ごとの都度交渉 | 「サンプルは全額前払い」「量産は前金50%」「少額なので分割せず納品後一括」が混在し、標準が不在 |
| 3 | 請求書の追跡単位が定まっていない | 取引先から「発注毎のメールを個々に追うのが難しい。件名に対象月を記載してほしい」との改善要請あり（2026-07-29） |
| 4 | 入金消込が目視・手作業 | 未入金3件・計¥5,745,861の督促で複数往復が発生。うち1件は既に相殺精算済みだった（当方の確認漏れ） |

**結論**: 自動化できていなかったのは技術的制約ではなく、**自動化の入力となる「型」が存在しなかった**ため。本書はその型を定義する。

## 2. 支払条件の標準（3類型）

**すべての案件は必ず A / B / C のいずれかに分類する。** 分類できない案件は §10 の例外処理へ回す。

| 区分 | 対象 | 請求タイミング | 支払期限 |
|---|---|---|---|
| **A: 全額前払い** | サンプル制作費、初期費用（金型代・刃型代）、開発着手金 | 発注書受領後ただちに100% | 請求日から **14日以内** |
| **B: 前金50% + 残金50%** | 量産、開発費、金型費など税込30万円以上の案件 | 前金: 発注書受領後ただちに<br>残金: 納品後 | 各請求日の **翌月末日** |
| **C: 納品後一括** | 税込30万円未満の少額案件、継続取引先のリピート案件 | 納品後 | 請求日の **翌月末日** |

### 2.1 適用の優先順位

1. 取引先マスタの `支払条件区分` に個別指定があればそれを最優先
2. なければ上表の金額基準で自動判定（税込30万円が閾値）
3. 先方から個別要望があった場合 → §10 例外処理

### 2.2 区分Aの着手条件

区分Aは **入金確認をもって生産着手** とする。請求書送付時点では着手しない。
文面に必ず次を含めること: 「ご入金の確認後、生産に着手いたします。」

### 2.3 共通条項（全区分・文面に必須）

- 振込手数料: **お客様負担**
- 消費税: 10%（軽減税率対象外）
- 見積書の有効期限: 発行日から **30日間**（為替変動リスクのため。延長要請は §10）

## 3. 請求書番号の採番規則

### 3.1 書式

```
CRS-{取引先コード}-{発注書No}-{枝番}
```

| 要素 | 規則 |
|---|---|
| `CRS` | 固定接頭辞（自社識別子） |
| `取引先コード` | 英大文字3桁。取引先マスタ §1.2 から取得 |
| `発注書No` | **先方の発注書番号をそのまま転記**。ハイフン・アンダースコアは除去し英数字のみ。発注書番号が存在しない場合のみ `YYMMDD`（発注書受領日） |
| `枝番` | `0`=全額一括（区分A・C） / `1`=前金 / `2`=残金 / `3`以降=追加請求・分割3回目以降 |

### 3.2 例

| ケース | 採番 |
|---|---|
| WILBY 発注書No.4002 の前金 | `CRS-WLB-4002-1` |
| WILBY 発注書No.4002 の残金 | `CRS-WLB-4002-2` |
| カイカイキキ サンプル全額（発注書番号なし・7/26受領） | `CRS-KKK-260726-0` |
| Horizon 発注書No.HZ03 の残金 | `CRS-HRZ-HZ03-2` |

### 3.3 不変条件（自動チェック対象）

1. **一度発番した番号は、金額・内容が変わっても再利用しない。** 訂正時は §6.7 に従い同一番号で「差し替え版」を発行する（番号は変えない）
2. 枝番の合計金額 = 発注書の総額（税込）と一致すること
3. 採番は §8.1 の請求管理台帳への登録と**同時**に行う。台帳に無い番号を送信してはならない
4. 先方の発注書番号を転記するため、**発注書PDF/Excelの番号を必ず原本で確認する**（2026-06-26の採番誤りはこの確認漏れが原因）

## 4. 件名・スレッド・Ccの規則

### 4.1 件名フォーマット（完全固定）

```
【御請求書】{YYYY年M月}分_{案件名}_{区分}_{請求書番号} / クロスイメージ株式会社
```

- `{YYYY年M月}` = **請求月**（請求日の属する月）。先方の月次締め処理に必要（MTR社要請）
- `{区分}` = `前金` / `残金` / `全額` のいずれか
- 例: `【御請求書】2026年8月分_AIMWIZフットレスト_前金_CRS-WLB-4002-1 / クロスイメージ株式会社`

他の書類の件名:

| 書類 | 件名フォーマット |
|---|---|
| 見積書 | `【御見積書】{YYYY年M月}分_{案件名}_{見積書番号} / クロスイメージ株式会社` |
| 入金確認 | `【入金確認】{案件名}_{請求書番号} / クロスイメージ株式会社` |
| 督促 | `【ご確認のお願い】ご請求分の入金確認について / クロスイメージ株式会社` |
| 訂正・差し替え | `【差し替え】{元の件名}` |

### 4.2 スレッド運用

**原則: 発注書を受領したメールへの「返信」で請求書を送る。** 新規スレッドを立てない。

理由: 先方が発注 → 請求 → 入金を1スレッドで追える。MTR社から明示的に要請され合意済み。前金・残金も同一スレッドに積む。

例外: 複数案件をまとめた督促（§6.6）と月次まとめ請求は新規スレッドで可。

### 4.3 Cc規則

| 種別 | 宛先 |
|---|---|
| 自社側Cc（**全送信メールに常時付与**） | `info@crossimage.jp`, `koizumi@crossimage.jp`, `chen@crossimage.jp` |
| 相手側Cc | 取引先マスタの `請求先Cc` + **受信メールに付いていたCcを全員維持** |

> 返信時に相手側Ccを削ると、先方社内の情報共有が切れて督促の往復が増える。**Ccは減らさない**を原則とする。

## 7. 送信前チェックリスト（6点・全項目必須）

請求書メールの送信前に、以下を**すべて**確認する。1つでも未確認なら送信しない。

- [ ] **①採番**: 請求書番号が §3 の書式に合致し、請求管理台帳に登録済み。**発注書原本の番号と一致**している
- [ ] **②金額整合**: 税抜 + 消費税 = 税込。前金/残金の場合は「枝番合計 = 発注総額」も検算

### 8.2 スケジュール（営業日ベース・自動実行）

| タイミング | アクション | 送信先 |
|---|---|---|
| D+0（請求書送付日） | 台帳に `入金待ち` で登録。Gmailラベル `01_請求/入金待ち` を付与 | — |
| 支払期限 −3営業日 | **社内リマインドのみ**（先方には送らない） | 社内 |

### 8.3 督促前の必須確認（誤督促の防止）

督促メールを送る前に、必ず次の3点を確認する。

1. 台帳のステータスが `相殺・精算済` でないこと
2. 当該取引先から `入金予定日` の回答が来ていないこと（回答済みならその日まで督促しない）
3. 該当スレッドに先方からの支払関連の返信が来ていないこと

### 8.4 入金照合のルール

- 照合キー: **振込名義 + 金額**
- 複数請求がまとめて1件で振り込まれる場合（HME社の「振込明細のご連絡」等）は、先方の明細メールを根拠に**手動で分割消込**し、台帳の `備考` に明細メールのスレッドIDを記録する
- 差額が発生した場合（振込手数料の先方差引など）は `差額` に記録し、¥1,000未満は経理判断で `入金済` として処理可。¥1,000以上は先方に照会する

## 10. 例外処理ルール

**自動化を壊す最大の要因は、その場限りの例外を記録せずに処理してしまうこと。**

### 10.1 例外の定義

次のいずれかに該当したら例外として扱う。

- 先方から支払条件（分割・期限・支払サイト）の変更依頼があった
- 標準の3類型（§2）に当てはめられない案件
- 相殺・値引き・生産中止に伴う減額が発生した
- 請求書の再発行・差し替えが発生した

### 10.2 処理手順

1. **その場で判断せず、まず台帳の `備考・例外` に事実を記録する**（依頼日・依頼者・内容・根拠メールのスレッドID）
2. 影響額が税込30万円以上、または支払期限が30日以上後ろ倒しになる場合は、**代表の承認**を得てから先方に回答する
3. 回答後、当該案件の台帳行を更新する
4. **同一取引先で2回以上繰り返された例外は、例外ではなく仕様である。** 取引先マスタの `支払条件区分` または `例外メモ` に恒久ルールとして昇格させ、以後は標準処理とする

### 10.3 既知の例外（昇格待ち）

| 取引先 | 内容 | 発生日 | 判定 |
|---|---|---|---|
| WLB | 少額案件は分割せず納品後一括請求 | 2026-07-31 | §2 区分Cの金額基準に統合済み |
| HRZ | 支払サイクル都合により支払期限を翌々月末に変更 | 2026-08-12 | **要観察**。次回も同様なら取引先マスタの支払サイトを「翌々月末」に変更 |
| MTR | 件名に対象月を明記／発注書メールへの返信で同一スレッド維持 | 2026-07-29 | §4.1・§4.2 の全社標準に昇格済み |

## 11. freee連携ルール

### 11.1 現在の制約（2026-08時点・期間限定）

弥生会計からfreee会計へのデータ移行（2026-07-16納品）において、**freee社側の作業ミスによりインボイス制度の経過措置（80%控除）の税区分が誤って登録された**ことが 2026-08-12 に判明。freee社が修正作業を実施予定（2026-08-21までに日程連絡）。

**修正作業日は、当日14:00〜18:00の間、以下の操作を行ってはならない**（freee社からの指示）:

1. 移行対象期間以前の期間へのデータ登録
2. マスタの設定内容変更（勘定科目・取引先・品目）
3. 口座の新規登録・口座の名称変更・口座種別の変更
4. 固定資産台帳の登録
5. 年度締め機能などによる年度の変更

### 11.2 移行期間中の運用ルール

- **freee側の税区分修正が完了するまで、freeeへの自動連携（API連携・自動仕訳ルール）を新規に構築しない。** 不安定な土台の上に自動化を積むと、修正作業で二重に壊れる
- この期間の自動化投資は、Gmail側（§9）と請求管理台帳（§8.1）に限定する。これらはfreeeから独立しており、修正作業の影響を受けない
- 修正完了後、メモタグ `データ移行サービス_税区分修正_mmdd` で絞り込み、当該仕訳の税区分・税額を経理と税理士で照合する
- 消費税申告について、freee移行後に申告を行っていた場合は**修正申告の要否を税理士に確認する**（freee社より要確認との指摘あり）

### 11.3 完了後の連携方針

税区分修正の完了確認後、以下の順で連携する。

1. 請求管理台帳 → freee の売上仕訳を CSV インポート（手動・月次）
2. freee の入金明細 → 請求管理台帳の消込を半自動化
3. 安定を確認してから API 連携へ移行

## 12. 自動化ロードマップ

| Phase | 内容 | 前提条件 | 効果 |
|---|---|---|---|
| **Phase 0**<br>即日着手可 | ラベル体系の作成（§9.1）／フィルタ12本の設定（§9.2）／取引先マスタの整備（§1）／請求管理台帳の作成（§8.1）／テンプレートの下書き登録（§6） | なし。**freeeの修正作業と一切干渉しない** | 状態が可視化され、埋没・失念が消える |
| **Phase 1**<br>freee修正完了後 | 台帳を起点とした督促の自動起票（§8.2のスケジュールをスクリプト化）／送信前チェック（§7）の自動検証 | Phase 0 完了 | 督促漏れゼロ。採番・金額ミスの機械検知 |
| **Phase 2** | 発注書メール受信 → 請求書の自動起票（採番・金額計算・PDF生成・下書き作成まで。**送信は人が承認**） | Phase 1 が3ヶ月安定稼働 | 1件あたりの作業時間を大幅短縮 |

### 12.1 自動送信に関する原則

**請求書・督促メールの「送信」は、当面すべて人の承認を経る。** 自動化するのは下書き生成・チェック・リマインドまでとする。

金額と信用に直結する文書であり、誤送信のコストが自動化の便益を上回る。Phase 2 でも下書き止まりとするのはこのため。
